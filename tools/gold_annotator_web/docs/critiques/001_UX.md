UX critique analysis and minimal, robust improvements

Goals
- Keep the tool fast and simple for gold creation.
- Implement only low‑risk, high‑leverage UX upgrades.
- Avoid brittle complexity (heavy state coupling, flaky async, or over‑engineered ML).

What we changed (safe, minimal)
- Drag‑to‑draw boxes: Click‑drag to create a box; small boxes auto‑discarded. Keeps creation fluid and predictable.
- Edge snapping to canvas: Snap start/end to page edges within ~6px. This helps clean alignment without complex box‑to‑box snapping logic.
- Persist per‑box metadata: `type`, `expected_json`, `part_idx` are stored with each box in `*.boxes.json` and round‑trip cleanly.
- Inline HUD: Lightweight on‑canvas editor for the selected box (ID, Type, JSON path, Save, Auto‑label). Reduces mouse travel and speeds up authoring.
- Heuristic auto‑label: Uses PyMuPDF text from the region and simple cues to suggest a type/path. Works offline; fails gracefully. No hard ML dependency.

What we deliberately did not add (to avoid brittleness/complexity)
- Box‑to‑box snapping and guides: Useful but adds visual noise and heavier geometry bookkeeping. We can revisit if strong need arises.
- Complex ID rename flows (e.g., collision checks, cross‑refs): We support renaming the box ID inline and keep selection in sync; additional constraints can be added later.
- Model‑backed auto‑labeling: Kept a simple heuristic path and a thin `/api/suggest` to plug a model later. Prevents coupling the tool to network/stateful backends.
- Aggressive auto‑path rewrites: We only set a default `expected_json` when choosing a type and the path is empty, to avoid surprising overwrites.

Notes
- Rendering is stable and crisp (HiDPI). We split PDF load vs render and reuse a single worker to avoid dev flicker and race conditions.
- Keyboard shortcuts: 1/2/3/4 for quick type, Cmd/Ctrl+S to Save, `A` to Auto‑label.
- Suggestions cache can be added later if latency becomes a concern.

Next candidates (still minimal)
- Drag‑to‑resize during creation (current flow finalizes on mouse up; transformation already supported after creation).
- Quick templates per type (pre‑fill `expected_json` with a doc+page scoped path pattern).

LLM vs. classic ML for table-to-JSON
- LLM (Gemini Flash 2.5 / GPT‑4o / Claude):
  - Pros: no training, strong few‑shot capability on varied table layouts, fast to iterate.
  - Cons: cost, latency, potential non‑determinism; requires careful JSON‑only prompts + schema validation.
  - Recommendation: enable as an opt‑in feature via `/api/extract-table` that calls a configured provider; validate output with Zod; show result in HUD for review before saving.
- Classic ML / rule‑based (Camelot/Tabula/PDFPlumber + OCR):
  - Pros: offline, predictable on digital PDFs with clear ruling.
  - Cons: brittle on scanned docs/merged cells/irregular structures; higher engineering overhead.
  - Recommendation: keep as fallback for native PDFs; avoid extensive investment initially.

Minimal path forward (low risk)
- Provide `/api/crop` (done) to return a base64 PNG of the region.
- Add `/api/extract-table` guarded by an env flag to call an external LLM endpoint; if missing, return a helpful 501 with the cropped image and a ready prompt.
- In HUD, a single "Extract" button triggers extraction and previews JSON; on confirm, save to `expected_json` path.
